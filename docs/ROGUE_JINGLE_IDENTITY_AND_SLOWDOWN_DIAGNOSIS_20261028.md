# Rogue canonical jingle-staff identity + bounded slowdown diagnosis — 28 October 2026

## Owner findings and proven cause

The 27 October owner-approved canon was clear *before* the Rogue public soft launch: [canonical handoff](ROGUE_BARD_CANONICAL_OWNER_HANDOFF_20261027.md) and [visual specification](ROGUE_BARD_STATIC_VISUAL_DESIGN_20261026.md) require a **staff bearing ONE oversized suspended spherical jingle bell** for normal and crowned Rogue. The [Phase 7 art record](ROGUE_PHASE7_PROCEDURAL_ART_20261027.md) and actual `src/prototype/visuals.js::rogueBellStaff()` implement that silhouette.

Yet `src/prototype/engine.js::enableRoguePlaytest()` added the generic `🔔` **ringing-bell emoji** to the class registry, which the class selector and HUD printed verbatim. In dev.207, the first visual/audio repair had initially conceptualized a conventional bell until a subsequent explicit owner correction. **This was not missing owner input.** The root failure was *cross-subsystem semantic drift*: the accepted weapon spec was enforced for world procedural art, but was not propagated/validated for UI iconography and combat feedback. Earlier rejected guitar paragraphs remain beneath the superseding note, which makes reading the active precedence critical; they were not the direct source of this emoji bug. Existing tests of Rogue admission even **expected** `🔔`, codifying the mistake, while procedural-art tests checked only the character drawing.

### Small correction and guard

Replace the Rogue class icon registry's emoji with semantic key `jingle-bell-staff`. The existing class-selector action and hero HUD use that key to show **one common, tiny SVG** of a crooked staff, suspended eye/string, and round slotted metal jingle ball, with accessible class-name text. Keep the existing class names, skills, artwork, audio, gameplay, saves and original three icons unchanged. Place the SVG in the single site-asset inventory so PWA offline and desktop/phone use the identical asset. A focused canonicity test now checks specification → registered key → menu/HUD → vector shape → offline asset inclusion, so future regressions cannot satisfy the earlier wrong-emoji assertion. This is a design-contract completion fix, not a broad redesign.

## Reporting shortfall confirmed in the owner's dev.206 JSON

The [uploaded first phone playtest report](ROGUE_FIRST_PHONE_ACCEPTANCE_20261028.md) documented two emergency entries (callback intervals **227 ms** at game 522.3 s and **205 ms** at 527.87 s), both followed by recovery. `performance.frameProfile` reports a rolling last-180-callback mean/p95 for frame, party AI, enemy AI and renderer. `partyDiagnostics` records current companion state, 0.5-second samples, Slow sources and emergency party snapshots. **What was missing:** a retained abnormal-callback record linking *that same callback's* interval, measured synchronous frame/AI/render/audio stage costs, whether simulation was actually held, current scene load and roster Slow/regroup state. The old report cannot identify whether the 227/205 ms callback gaps were caused by simulation work, companion AI, layout/render work, browser scheduling or another source. No GPU time or per-companion CPU telemetry is available; do not invent those conclusions.

### Small reporting extension, no new workflow

The existing **Save and game management → Export playtest report** JSON now gains `partyDiagnostics.performanceIncidents` and `dropped.performanceIncidents` without changing the save schema or creating another settings page. Only abnormal active callbacks qualify: **interval ≥140 ms**, or **measured synchronous frame work ≥45 ms**, or **companion update ≥20 ms**. Each captures the *same callback's* work/interval, stages (simulation, companion, enemy, other simulation, renderer, audio, event dispatch, HUD, other JS), renderer/optimization/draw/emergency flags, bounded encounter counts, and existing party snapshot; no repeated per-unit timing claims. The event history is **max 16**, with **500 ms rate limiting** for moderate incidents and a dropped counter. Hard callback gaps (≥180 ms) and large work spikes (≥90 ms) bypass rate limiting. No routine-frame roster traversal, network upload, persistent records, new browser workflow or underlying AI behavior changes.

This is enough evidence to select the **next narrow targeted investigation** if an actual new phone slowdown occurs. A callback gap with low synchronous frame work suggests a browser scheduling/background/other outside-frame stall candidate; a high matching `companionAI` stage suggests looking inside `updateParty()` next; a high `render` stage suggests renderer instrumentation. These are hypotheses, not automated root-cause verdicts.

**Limitations:** No current capture can retroactively recover which dev.206 callback consumed the CPU. The incident sample is observational and is not a system profiler: browser GPU, OS, garbage collection, individual companions and external main-thread tasks are not directly attributed. Export after observing the next slowdown, ideally without closing the app first. Playtesting stays on the **normal published game**, as the owner requested.
