The 83 current music cues were composed and rendered with original deterministic virtual instruments. They were not downloaded from a sample library or generated by an audio model. The exact recipes are `tools/audio/score-book.json`: title, BPM, root, mode, instruments, melody, role, flavor and bars. `render-score.py` supplies the chord progression, articulation, percussion, synthesis and mastering. Every current recording has a `generationGuide`; `director.eventGuides` currently contains 95 event guides. **The pre-existing generation guides and old scorebook templates were written before the latest canon/worldbuilding passes; they are not the approved soundtrack's future emotional authority.** Use the 26-family [current sound bible](AUDIO_SOUND_PASS.md) and 14 explicit owner choices in #673 before composing or rewriting any of the 65 included tracks. These are reusable natural-language briefs written after creation, explicitly distinguished from historical model prompts by `creativeSource`. They can guide an external audio tool or a composer, but do not reproduce exact PCM. The listening room displays/copies the selected recording guide and every effect guide. Editing a guide alone changes descriptive metadata; editing the composition/synthesis recipe and rendering is what changes the sound.

For a small musical adjustment **within the included 65-ID allowlist**, retain the cue ID, edit its score-book recipe, then render that cue with `python3 tools/audio/render-score.py --cue <id>`. Rendering requires numpy, scipy and ffmpeg. Related layers must keep the same tempo and loop duration. If those change, render every affected base/action/night/refuge/boss layer before the build. An ordinary melodic or instrumentation edit can retain the existing layer timing. Update the guide if its creative description changes.

## Standing soundtrack quality gate

**Why this was added:** The initial eight Phase 2 pilots passed MP3 rendering, sync and waveform checks, yet the later score audit exposed repetitive arrangements, weakly reviewed melody/chord relationships, uncertain continuity with the original themes, limited dramatic action/TRUE development and unverified synthetic timbres. These defects of *process* should have been caught by the producer before scaling. See the concrete [pilot corrective issue #701](https://github.com/joedoragon-glitch/azeroth-chronicles-prototype/issues/701) and [Phase 2 source audit below](#pre-phase-3-musical-quality-audit--31-october-2026). **This standard is an automatic engineering/creative responsibility, not an optional owner-requested audit and not a new owner approval meeting.**

**Work like a composer and sound designer, not a batch-file generator.** Before writing any family, read the current world/quest/character source, the [26-family sound bible](AUDIO_SOUND_PASS.md), Q01–Q14 and the existing recording/score book. Write the *sound of the scene* in production terms: whose point of view the music occupies; emotional contradiction; what the player must notice; a motif that makes this place/character recognizable; how the loop evolves; what combat/TRUE/global peace changes; and which audible sounds, instruments and spatial texture communicate that intent. **A narrative paragraph or different instrument name is not itself musical execution.**

**Composer-level gates applied independently to every family, then to the entire collection:**

1. **Identity and source truth.** Give the place/boss an identifiable interval/rhythmic hook and a musical reason for it. Map the old recorded hook to *retain, transform or consciously replace*; document the decision. Never substitute medieval/fantasy generic cues, a character caricature, retired lore, or unexplained emotion for present canon. Track the shared former-companion idea without precomposing frozen Crown themes.
2. **Actual musical craft.** Review the written notes and hearing-oriented intent, not just a valid score schema. Check harmonic function and voice-leading; bass direction and chord rhythm; melody against the chord on accented/sustained notes; approach and **resolution** of deliberate dissonance; repeated motif development, call/response, silence, cadences and contrast. A dissonance percentage is a review prompt, **not** an automatic artistic failure rule. Distinct chord arrays with the same unvaried melody/ostinato are **not** sufficient evidence of distinct compositions.
3. **Form and pacing.** Sketch opening → development/contrast → arrival/return/transition, including density, registration, phrasing and dynamic contour. Account for repeated 30–60 second loops and longer play sessions: avoid a fixed unvarying pattern every bar and cheap “louder = more dramatic” escalation. Arrange silence intentionally; don't let a loop reset erase musical momentum.
4. **Orchestration and sound quality.** Evaluate expressive tone, attack/release envelopes, instrument voicing, articulation, velocity/timing humanization where musically appropriate, spectral balance, bass, reverb/space, masking and how a sound reads on small speakers and headphones. A 96-kb/s mono preview, original oscillator instrument, clean decode or normalized RMS **cannot** prove a pleasant, rich or professional-sounding recording. Improve synthesis/arrangement when required; do not hide weak sound behind broader reverb, generic pad layers or volume.
5. **Interactive scoring.** Treat base/action, boss/TRUE and global-peace as meaningful *dramatic states*. Action/TRUE must transform pressure, texture or motif in a character-specific way, while preserving matching musical clocks and warning/intelligibility headroom. Global peace is **only** the actual post-ending state and should remain fragile where Q11 requires; a bright major chord or duplicated base with fewer drums is not by itself a post-ending arrangement.
6. **Critical comparison, not self-certification.** At pilot and each delivery-family checkpoint, compare the *actual score source* to (a) the approved brief, (b) existing theme and (c) other newly authored families. Look for sameness across places, weak motives, unresolved tension, mechanical rhythms, dubious timbres and misplaced drama. Have the author attempt to **disprove** each composition's suitability. An independent review or *actual internal audible A/B* is valuable where technically possible; document what was really heard and on which files. **Never invent a listening impression** when audio playback/ears are unavailable. ## Add or replace recordings

Place the approved local file beneath `assets/audio`, then use the registration helper. It measures duration using ffprobe, computes SHA-256, retains compatible metadata, validates the entire proposed catalog, and writes atomically. Registration removes score-renderer ownership and old codec variants, and marks the entry as an imported recording. Add replacement codec variants explicitly after validating their duration/loops. Existing IDs retain their triggers.

```sh
npm run audio:register -- steel-hit assets/audio/effects/steel-hit.wav --kind effect --author "Joel" --license "CC0-1.0"
npm run audio:bind -- effect.heroSteelImpact steel-hit --gain 0.22 --when '{"actor":"hero","class":"paladin"}'
npm run audio:register -- place-vale assets/audio/music/new-vale.mp3 --kind music --bpm 92 --loop-start 0.15 --loop-end 21.0195625
```

The sample loop bounds are illustrative; use measured musical bounds for the actual replacement. Supply author/license for a new asset. Existing provenance is retained unless replaced explicitly. Replacing synchronized layers with different timing/tempo requires an atomic batch: `node scripts/audio-library.cjs batch registrations.json`. The file is an array of `{id,file,kind,bpm,"loop-start","loop-end",author,license}` records; optional fields can inherit existing metadata. All entries are validated together before the catalog is changed.

The renderer refreshes only assets marked `managedBy: "score-book"`. Imported additions, replacements of existing IDs, custom routing, credits and edited generation guides survive full/partial regeneration. An owned cue removed from the score book leaves the catalog on a full render; references to it must be removed or redirected before publishing. The renderer refuses to overwrite a file referenced by a custom sound.

## Music and sound routing

`director.places` maps each location to base/action/peace/night/refuge assets and optional `gain`, `nightGain`, `settlementGain`, and `fade`. `director.bosses` maps normal/TRUE layers with `gain`, `idleGain`, `trueGain` and `fade`. `director.specials` selects title, defeat and finale assets/gains. Place fallbacks use zone, then region, then `fallbackPlace`. A new location can use new or existing registered tracks by adding one location entry; a boss can use a new normal/TRUE pair by adding one family entry.

Music selection has one owner when production is enabled. Explicit `setRecordedCueRules` overrides take precedence, followed by first-match `director.rules`, then the standard special/boss/location policy. A rule is `{id,when,score:{stems:[{id,gain}],bpm?,fade?,quantizeBars?}}`; BPM may be inherited from its first asset. Match fields are region, zone, interior, settlement, situation, night, peace, bossFamily and bossForm. Put specific rules before broad ones. Custom rule gains are respected rather than overwritten by automatic combat intensity. Disabling explicit overrides restores catalog routing.

`director.events` contains ordered first-match arrays under `effect.<soundKind>`, `interface.<action>`, `step.<surface>`, and `ambience.<detail>`. Empty arrays retain the current synthesis. Each binding specifies `{asset,when?,gain?,bus?,pan?,minGap?,priority?}`. Event conditions add actor, class, role, species, style, special, combo and surface to the scene fields. Inspect existing keys for supported identities. Deliberately silent engine events remain silent; combat classification and gameplay timing stay in their existing owners.

Automatic events use decoded recordings synchronously when ready. A cold event plays its original sound immediately while warming the recording for the next occurrence; completion never replays an old click or hit. At most two effect warm-ups run together, retaining queue space for music. Deferred events may warm on their next occurrence; failed warming is bounded to one attempt per asset until catalog replacement/reopening. The existing event throttles, warning duck/priority, victory timing, voice limits, bus routing and mute/pause rules still apply. Automated event recordings are one-shots even when the asset has loop metadata; continuous environmental beds have their independent catalog-driven owner described in `AUDIO_ENVIRONMENT.md`.

## Replacement, release and resource contracts

`configureRecordings` validates before stopping existing music. It then cancels old sources/requests, resets catalog selection/failure state and enables the current scene to restart against the new snapshot. Pause/resume retains an already active group's position. Invalid replacements leave current playback intact. A failed valid asset request returns to procedural music without a per-frame retry.

Run `npm run audio:check` for validated file counts and encoded headroom. The audio manifest currently registers 127 assets: 83 music cues, 14 environmental beds and 30 effects (approximately 24.5 MiB of source files), under the historical 32 MiB total/8 MiB file/32 MiB decoded caps at its source checkpoint; published main now uses **256 MiB total, 16 MiB per file and a 96 MiB default decoded cache**, pending reconciliation into the older stacked Phase 3 branch. Creative metadata has a separate 256 KiB catalog limit; unused creative text is omitted from generated selection data. All registered files are precached, so expanding the library affects offline installation size. This housekeeping does not introduce streaming; long stereo recordings can exceed decoded/crossfade memory even when compressed files are small.

For *gameplay/audio-asset* edits that have received the necessary separate authorization, update package/package-lock build versions with the required development-state marker, run the smallest relevant tests and focused build checks, then seek approval before merge/publication. **Documentation-only Phase 1 work does not need an audio rebuild or version bump.** The versioned service worker fetches new assets and removes the old cache on activation; reloading installs the coherent new runtime/catalog. Copying a file over an old filename without updating hash/version is not a release workflow. See `AUDIO_PLAYBACK.md` for detailed transport and memory contracts.
