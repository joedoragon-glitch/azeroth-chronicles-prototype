# PR #570 cross-region changes — before/after and selective rollback review

**29 October 2026 · dated source-change audit · draft rollback preparation, NOT a code rollback.** The game's official title is *So I Became the Dark Lord's Problem*. This document audits **non-Greenwood changes introduced with the merged Greenwood flagship PR #570**, not all historical improvements to these regions. No non-Greenwood design has been judged bad merely because the owner rejected the flagship's visual implementation.

## Reason for review and exact source boundaries

The owner rejected Greenwood dev.233's environmental/artistic implementation after an iPhone playtest and asked that the other regions' accompanying modifications be documented **before any rollback decision**. ## Why a blanket rollback is unsafe

A whole `git revert -m 1 323bb2a7` would remove the **entire** Greenwood release as well as these cross-region repairs, affect build/asset/version/documentation changes and conflict with later `main` work. Resetting `main` to the old SHA would also discard unrelated releases, including dev.234 companion improvements. Neither is an appropriate non-Greenwood-only remedy.

Even a precise code revert can leave **already-migrated v4 saves** with moved road vertices, props, service positions and receipt fields. Existing code **cannot be assumed to run those migrations backwards**. Removing a version flag is not a reverse migrator and might run an old mutation twice. Preserve pre-upgrade exports; never overwrite a newer player save just to reproduce historical visuals.

## Selective rollback design — draft review gate

**Default: preserve all non-Greenwood source until each regional before/after image, route and save delta is measured and reviewed.** A successful automated road audit is evidence of road assertions, not an owner request to redesign another province.

1. **Freeze baselines and classify.** On an isolated read-only checkout, materialize fresh seeded games and at least one genuine protected v4 backup for each other region (when available) at `87792f64` and `323bb2a7`. The 29 October historical branch `recovery/greenwood-pre-flagship-20261029` is *earlier* than immediate pre-merge and must not silently substitute for `87792f64`. Keep copies isolated to prevent automatic migrations from mutating the original backups.
2. **Compare same scene/seed/zoom.** Capture town/refuge/hamlet, major transport and bridge, Treasury, representative creature habitation, road joins and wilderness. Produce a before/after position census by stable prop/NPC/road ID (including counts added, moved, removed), collision/clearance and native route results. For Frontier/Crown specifically, record all objects changed by the shared finalizer, not just the anchor services.
3. **Make region-by-region dispositions.** Mark each difference **retain**, **rollback**, or **redesign separately** using evidence and the existing approved regional visual contracts. Preserve already-acceptable parts; do not substitute automatic road expansion for human review. Avoid rolling back fixes that prevent trapped players without first providing an alternative safe approach.
4. **Prepare the actual rollback implementation in this separate draft PR only after determining the exact wanted deltas.** Isolate removals/replacements by region; avoid a whole-merge revert. For new games, restore the original authored result only for selected regions. For migrated saves, choose between explicitly tested reverse positioning of existing stable IDs/roads and preserving the upgraded geography with accurate disclosure. Never delete player Barracks, quest progress, saved actors, crowns or discoveries.
5. **Validate focused and source-first.** Original `town-street-audit`, `local-sites`, `ironroot-highlands`, geographic route/entrance checks and **pre/post repeat-restore v4 tests**, plus exact same-camera screenshots and offline build, must be reviewed on the rollback head. If a previously green strict road assertion becomes red, do not weaken it; explicitly demonstrate the pre-change routing was acceptable or design a narrow alternative.
6. **Publish only with owner authorization.** After final branch and test receipts, the owner decides if the before/after is actually preferable. No merge, automatic Pages deployment or device verification is implied by this draft.

## Owner's clarified road criterion — identify engineering repair versus overbuilding

**Later owner direction, 29 October 2026:** A genuine impassable road, painted building occupying a road, or unusable doorway should be repaired. **Do not turn the province into a fully connected city-simulation street graph simply because a test insists every individual road component touch the town; do not relocate otherwise-acceptable buildings to accommodate roads that should not have been added.** Existing regional compositions are presumptively acceptable until specific evidence contradicts them.

**Source-confirmed candidate for selective rollback:** The new #570 shared `world.js::clearStreetCorridors(z, true)` pass is invoked after outdoor regional composition, except in Greenwood. It uses `distanceToRoad(z, major) >= 1` to connect a town square, then repeatedly searches **all** road components and appends collision-routed joining spurs until `connected.size === z.roads.length`. The same pass can reposition previously authored service NPCs, saved Barracks and roadside props to satisfy new road artwork footprints. For `frontier`/`crown` it persists selected new NPC positions into `frontierTownPlacements`/`crownTownPlacements`. These are concrete **automatic expansion and relocation mechanisms**, not evidence that a player couldn't reach a named destination before #570. **Classify them as owner-rejected in principle pending exact source-by-ID delta / save safety evidence**, not as design requirements to retain merely for a green road-network assertion.

The existing `town-street-audit.test.cjs` asks for **every road** to belong to one town-connected network. That test embodies the stronger assumption. A disconnected ornamental/spur segment may be acceptable when actual town, refuge, doorway, bridge, transport and quest destinations remain traversable. Future validation must keep **real reachability and collision** checks intact, and must not falsely claim that the old test passes after returning to the owner's weaker visual/network requirement. If a historical requirement in the older merged road-audit contract conflicts with this newly clarified owner direction, update only the relevant assertion **with a demonstrable native-route replacement**, and retain original failure evidence.

| Classification | Candidate disposition | Reason |
| --- | --- | --- |
| Actual blocked walkable road, bridge, Treasury door, refuge or essential destination | **Retain or minimally repair** | Gameplay/collision/access evidence, if reproduced on the exact pre-merge state |
| Short direct connection to an isolated *required* settlement where no actual route exists | **Conditional retain** | Marches Reedport 270-unit link and Highlands quarry 140-unit spur require native destination tests and a same-camera visual review |
| Shared graph-saturation connector `clearStreetCorridors(z, true)` linking every road regardless of purpose | **Selective rollback candidate** | This adds potentially arbitrary roads and is stronger than the owner's requested navigability |
| Settlement/service/building/prop moves caused *only by newly forced connectors* | **Rollback candidate with saved-state reconstruction** | Should not keep secondary disruptive changes when the triggering extra street is removed |
| Highlands Treasury carriageway roof overlap and genuine existing-street obstacles | **Conditional retain, minimum fix** | Remove actual obstruction without importing an unrelated scene redesign |
| Highlands ogre scene / broad prop fan-placement without demonstrated actual obstruction | **Review individually** | Large world-life relocation and final roadside pass may change already-serviceable visual identity |
