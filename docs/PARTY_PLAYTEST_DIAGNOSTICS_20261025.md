# Companion and pet playtest instrumentation — dev.181 (25 October 2026)

## Purpose
An owner playtest in Greenwood Vale produced repeated Goblin Rogue warnings, accumulating Slow and cooldown recovery debt, low issued-draw cadence, and five emergency-performance entries. The original JSON exported full hero status and aggregate `frameProfile.companionAIMs` but lacked per-companion and pet state/history. **This change adds diagnostics only.** It does not tune Rogue cadence, Slow, skills, movement, AI, or emergency thresholds.

## New JSON field
`partyDiagnostics` is exported alongside `hero` and `statistics` from **Save and game management → Export playtest report**.

- `current`: all rostered companions, including benched units, and boss pets with `petFamily`. For each: identity, active flag, health, coordinates, Slow duration/stacks, Rogue Slow duration, effective slow movement factor, current cooldown recovery factor, relevant cooldown timers, order/target/charge/critical/regroup/recall states.
- `samples`: every 0.5 seconds of *completed simulation time*, containing active units only; 120 most recent snapshots (up to about 60 seconds of continuous simulation). Skipped draws do not reduce observation frequency. Paused/menu/background/emergency-held callbacks do not add fake simulation samples.
- `slowApplications`: up to 128 successful party Slow applications with target, resulting cooldowns and stacks, duration and hit-time cooldown debt. For Rogue actions the source enemy ID and maneuver name come from the actual resolved attack, rather than inferred overlapping warnings. Other Slow origins remain labelled `other` with no fabricated source.
- `emergencyTransitions`: up to 16 transitions, each recording the entering/recovered status, callback interval, emergency entry counter, and the entire party state even if the simulation cannot advance.
- `recoveryActions`: up to 12 pre-action snapshots for attempted encounter disengagement and refuge returns.
- `dropped` counts evicted old samples/events to avoid hiding truncation. These buffers exist in a per-Campaign WeakMap and are never persisted in the save format.

## Interpretation
`performance.frameProfile.companionAIMs` still measures **all** of `updateParty()`, including targeting, movement, combat and bookkeeping. It is **not** CPU time per companion/pet and does not establish that being Slowed caused high CPU use. This instrumentation captures correlations between hits, conditions, cooldown behavior, emergency activations and overall party cost; it does not claim per-unit CPU causality or substage profiling. Emergency records capture the last observable state, not the browser's internal reason for a stall.

## Owner reproduction
After receiving the dev.181 game update, open an existing run, approach the Greenwood Vale Goblin area with a Soldier, Archer and/or boss pet, allow the enemy warnings to land, observe recovery/emergency events, then use **Export playtest report**. A single report includes the latest bounded session observations, active and benched roster statuses and the original performance measurements. Keep the game running until export; closing/reloading starts a fresh transient diagnostic session. No new menu setting or opt-in recording is required.

## Validation scope
Focused regression test: `node tests/party-playtest-diagnostics.test.cjs`. It verifies Soldier/pet attribution, cumulative Slow, unchanged campaign snapshot, bounded history, emergency transitions, browser frame integration and paused/menu suppression. Existing Slow/cooldown and emergency tests remain relevant; full-game and browser matrices are explicitly outside this narrow change unless authorized.

## Automatic startup and foreground history — #841/#842 dev.265 candidate

The existing **Export playtest report** action adds `performance.startupDiagnostics` to the same JSON file. Report keys, milestone codes and diagnostic explanations are English only, independently of the chosen game-interface language; nothing is duplicated in English/Spanish. Recording is always automatic, before the other game scripts; never ask the player to enable profiling, make a move, or export a second file. Existing optional renderer/effect/navigation profilers retain their own independent controls and costs. This field records the latest three document/Continue/foreground attempts, with at most 48 milestones per attempt and a 32-KiB ASCII-only stored envelope, in `sibdlp-startup-history-v1`, separate from v4 campaign saves. Entries expire after seven days. Repeated state is coalesced; there is no timer, continuous frame trace, GPU readback, input/key recording or automatic upload.

Milestones cover document/DOM load, core script/style failures, app entry and build identity when available, Canvas context, save selection/writer ownership, update gate, title, New Game/Continue, sprite settling, save recovery, graphics preference/hold/failure codes, GPU preparation, first scene draw/reveal, audio waiter, controls, first normal draw and actual native-input movement if it occurs. Opening the map is also observable. Standing still yields a completed scene startup without inventing movement. `ready` means the normal scene gate completed; a first live draw measures synchronous submission, not proof of monitor/compositor pixels. Sprite/audio waiter settlement does not promise every optional asset succeeded or sound played. Renderer root error details remain in the existing graphics diagnostics.

Brief returns are distinguished from sustained hidden → title → guarded Continue. Visibility/BFCache notifications for the same return coalesce. A failed boot can leave evidence for a later working export: milestones are checkpointed before expensive preparation, and an unfinished previous document is labeled interrupted without inventing a crash/GPU cause. The first failure stays separate even if the bounded event list drops middle milestones. Reports include dropped counts, limits and storage-write status. Blocked/quota storage does not stop the game; in-memory diagnostics still export but may not survive another document. No recorder can log a navigation before its own script runs, a failure to load that recorder, or unflushed work after a hard browser/process kill. Simultaneous tabs are best-effort last-writer history, never a campaign authority. No retroactive history is fabricated for older installed builds.

Acceptance uses native lifecycle/storage/refusal tests plus one focused browser case: abort an engine script before app startup, reload into an ordinary Developer Mage game, observe a complete startup while idle, exercise real movement and the map, and download the single existing report without enabling any profiler. The existing Pixi/default/fallback, saves, menus and PWA checks remain required; physical desktop/phone behavior is not certified by software-browser tests.

### Settings and browser/device audit in the same report

The report's `settings` object records display language, selected/effective screen mode, camera zoom, all input preferences/bindings, reduced-motion preference and the relevant succession/squad/fallen-charm options. Its `capturedAt` identifies the export-time snapshot: it is not a claim that these values applied to an earlier retained startup. Existing canonical `audio.settings` contains sound levels/mute and `performance` contains chosen/effective renderer, optimization, FPS, frame skipping and resolution; `settings.references` points to those sections rather than repeating their values. Tests deliberately change sound/performance choices before export and check the actual values, including the Spanish interface with the same English report keys. Export never applies or resets options.

`performance.environment` retains bounded user agent, browser-reported CPU concurrency, coarse RAM and viewport. Its `device` adds available low-entropy browser brand/platform hints, touch capability, screen dimensions/color depth and optional JavaScript heap estimates. Null means unavailable, not evidence of a missing feature. Exact device/CPU models are explicitly unknown: browser APIs cannot reliably identify a retail Chromebook/laptop or total local equipment health. Browser values may be masked, coarse, reduced or spoofed; heap readings exclude GPU/driver/browser process memory. No device identifier, permission prompt, high-entropy API, system scan or automatic upload is added.

`performance.graphicsRenderer.deviceGraphics` caches the last successfully initialized actual game WebGL2 context's version, reported/masked vendor/renderer, optional unmasked GPU description and texture/renderbuffer limits. This is one bounded observation of an existing context, not a new GPU probe, benchmark or proof of current graphics health. `observedAt` and the note remain with the cached facts if a later fallback occurs; no actual successful context means null. Startup state milestones also retain viewport/backing dimensions, recovery attempts and bounded first error/source basename/line/column where available. Error URLs are removed; neither full URLs nor stacks are copied into the new journal.
