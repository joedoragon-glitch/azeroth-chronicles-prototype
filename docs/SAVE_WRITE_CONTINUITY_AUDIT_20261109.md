# v4 save-write continuity audit — 9 November 2026

**Milestone:** v0.9.2 functional completion. **Baseline:** published `main@e97dd771190ee83f37fc61d091671e4d110c3a36` (`0.9.1+snapshot.dev.288`). **Change owner:** [PR #864](https://github.com/joedoragon-glitch/azeroth-chronicles-prototype/pull/864), [original issue #634](https://github.com/joedoragon-glitch/azeroth-chronicles-prototype/issues/634). This is a **source and focused-native audit of the campaign's explicit validation limits, active producers, snapshot/export path and storage failures**. It is not a claim that every future bug or device-specific failure has been excluded, nor evidence of an ordinary player encountering an extreme stress scenario. The PR remains **unpublished** until a separately approved merge and exact-main deployment.

## What the audit means by “can no longer save”

A *gameplay-created unsaveable state* arises when legitimate game methods mutate `Campaign.s` so that `Campaign.validate(game.snapshot())` throws. In that case `persistence.save()` returns false, the previous local primary remains, and **manual external export also rejects the invalid snapshot**. This is more serious than an optional recovery-checkpoint warning, a deliberately fenced second browser tab, or an operating-system quota/eviction event. All four cases require distinct handling.

**Real source path:** `src/prototype/save.js::snapshot/validate/restore` → `src/prototype/persistence.js::writeSnapshot/save/prepareExternalExport` → `src/prototype/app.js::save/background lifecycle`. The v4 validator stays strict; silently relaxing it would turn write failure into unbounded or unrecoverable saves.

## Writer, storage, and user-visible failure classes

1. **Validation/serialization refusal:** `writeSnapshot()` validates *before* `localStorage.setItem`; invalid state cannot overwrite the previous known-good primary. `prepareExternalExport()` validates too, so prevention at source (as above) matters more than displaying a generic “Export” workaround. A newly introduced cyclical runtime object could make JSON cloning fail before validation; the current saved state is intended to use plain data objects, and no native cycle producer was identified here. New modules must retain this invariant.
2. **Browser quota / disabled localStorage / eviction:** Primary writes can fail for environmental reasons, independent of validator correctness. Quota-specific retry discards an optional recovery checkpoint first, then tries the authoritative primary; failure preserves its previously durable bytes. A valid snapshot can still exceed a browser's storage allocation. Permission to use persistent browser storage is best effort; **external file backups remain necessary**.
3. **One-minute recovery checkpoint and 2,000,000-character guard:** Optional checkpoint rotation is bounded to one validated entry and rate-limited. If too large or quota fails, primary saves still succeed and a warning recommends external backup. This is a *recovery-depth limitation*, not the Ringleader failure.
4. **Concurrent tabs / stale writes / unreadable original:** Writer ownership, expected-raw revision checks, and protected invalid-slot replacement deliberately refuse risky overwrites. The correct action is to load the current owner or explicitly recover/import, **not** bypass the lock to claim a write succeeded. Existing `persistence-safety`, `save-writer`, restart/recovery, and conflict tests own these contracts.
5. **Profile-only failure after a committed primary:** Previously `persistence.save()` returned **false** if optional profile preferences could not be stored, even though the actual campaign primary had already been written. This could trigger a misleading “saving failed” pause. PR #864 now reports success for the authoritative primary, while surfacing a critical warning that preference storage failed and an external backup is advisable. This does not weaken profile error handling when saved independently.
6. **Browser interruption before the next successful save:** There is no promise that an OS suspension/crash preserves in-memory actions after the last durable checkpoint. Background/visibility and restart guards already attempt a protected save and offer recovery/backup controls. Those paths are audited as safety boundaries, not treated as bugs simply because a second tab or storage-denied browser refuses to write.
7. **Version/cache/update handoff:** The game's fixed PWA cache-version identifier, content-fingerprinted scripts and exact-main Pages release identity are separate. This PR updates generated `sw.js` fingerprints for changed code, but does **not** bump to v0.9.2, publish, prove an installed device refreshed, or authorize a main merge.

## Residual risk and follow-up

No finite validator can mathematically guarantee that every theoretically unbounded number remains in range forever. The practical audit targets **known gameplay producers able to cross finite save limits without an upstream guard** and the browser adapter's existing failure surfaces. The handful of far-out numeric saturation cases, future authoring changes, operating-system eviction, deliberately stale second tabs and an invalid external import remain separate from the fixed, reproducible gameplay-created save refusals. Future reproducible real-player save failures should include the **loaded SHA**, exact status, active mode/zone, attempted save versus export, last good backup and relevant state counts; do not request a complete save file publicly without privacy review.
