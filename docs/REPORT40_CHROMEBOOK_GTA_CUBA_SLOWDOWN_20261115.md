**Status: targeted investigation ongoing; exact root cause NOT established.** Updated 15 November 2026 after direct reinspection of the original owner JSON, the corresponding loaded source, current `main`, prior decisions and open PRs. - The owner requested **source-led analysis using this report before more repetitive physical playtests**, and the smallest useful diagnostics rather than burdensome profilers. The ultimate goal is to isolate an actual root cause, not just suppress symptoms or endlessly optimize.

## 3. Priority hypotheses and counterevidence

**A. Movement-linked guide/quest route recalculation — high-priority candidate, NOT proven.** In `src/prototype/app.js`, `updateNavigationGuide()` recomputes `game.navigationTarget(guide.destination)` when a non-autopilot guide is sufficiently old or the hero has displaced 100 world units; `updateQuestGuide()` can also recompute routes when the hero moves >100 units relative to its route origin. The retained large-stall positions advance in approximately 100-unit steps. These functions run in the frame after the timed simulation segment and before rendering; route calculation could land inside `otherJsMs`. **Missing evidence:** whether either guide was active at the incident; whether `game.navigationTarget()` / `game.route()` actually executed; the route duration. Avoid changing path geometry or quest guidance without verifying.

**B. First-use/visible procedural Pixi artwork — possible contributing workload, NOT a verified recurrent cause.** `pixi-experimental.js` reports 3,046 cumulative procedural bakes (~32.8 **seconds summed across the entire session**, maximum single measured bake ~70.6 ms), 409 prepared neighborhood entities (~4.24 seconds summed), 494 procedural GPU-prepared textures, ~252 MB estimated retained procedural image bytes. A bake does not equal one stall. Visible live actors/FX can still require new art despite startup preparation. The most severe work was often recorded on frames with **no Pixi draw**; those particular residual spans are not explained by the named Pixi `draw()` stage. Async idle work may instead create callback gaps; cross-check distinct timestamps, not unrelated cumulative totals.

**C. Autosave/event-triggered full campaign serialization — mitigation justified, causal link unverified.** Existing normal periodic attempts every **five game seconds**; event-triggered progression/action saves can happen separately and were not timestamped in the private report. The worst repeated residual spikes over ~3 game seconds are too frequent to be explained *solely* by the periodic five-second timer. A hidden direct save/GC workload remains possible, but event absence is not proof a save did not execute. Owner requested skipping ordinary periodic, progression and action full saves during combat; preserve essential recovery/event writes. See unmerged separate [PR #873](https://github.com/joedoragon-glitch/azeroth-chronicles-prototype/pull/873) for the narrow save policy, EN/ES switch, explicit 60-FPS opt-in, and bounded session-only `performance.saveDiagnostics`. That PR is **not in this branch or the custom GTA Cuba build**; never confuse CI green with measured FPS improvement.

**D. Optional predictive preparation, cache scans and combat overlap — confirmed avoidable-work gap; causal link unverified.** Startup/region arrival prepares all *admitted* actors and props, plus static region terrain. Predictive idle work still scans and sorts candidates after ~180 world units of travel, even if every candidate is already cached. It skips baking existing revisions but may waste enumeration/sorting, Set allocation and full-dictionary difference scans. Existing `nearActiveFight` checks reject pending callbacks at entry and after completion, yet the asynchronous `warmNeighborhood` loop formerly did **not** recheck combat immediately after each yielded batch. A scan started outside combat could therefore resume optional baking during a fight. This is a source-level gap worth narrowly fixing. The private report contains **no per-predictive-run attempted/new/skipped breakdown**; its aggregate bake/hit counters cannot answer whether past predictive scans found new assets.

**E. Garbage collection/browser scheduling, other JS after `game.tick()`, or build-specific GTA Cuba interactions — unverified.** Repeated large residual `otherJsMs` is consistent with several possibilities; do not label it GC without browser evidence. There is no controlled matched-build report showing the GTA Cuba controls patch caused the issue. Keep movement-triggered basic attacks, controls and normal combat mechanics unchanged.

## 4. Reconciliation of whole-region caches vs predictive work

These are **different resource layers**, not a contradiction:
- **Static terrain/roads:** `prepareTerrainTiles()` builds the active major-region atlas (separate admitted interiors may be cached), not five major regions at once. During play, `syncBackground()` composites tiles into the reusable viewport texture. Report (40): 119 prepared terrain tiles, 152 tile reuses, **one background repaint** and **zero background lookahead paints/promotions**. With a valid terrain atlas, the old camera-lookahead painter is normally bypassed.
- **Admitted procedural actors/props:** `warmNeighborhood(epoch, true)` prepares all current-zone admitted eligible identities before gameplay reveal; recognized approved sprite assets load separately. Cache hits and retained identities avoid repeat bakes for known revisions.
- **Predictive work:** `queuePredictiveWarm()` on outdoor travel scans prospective offscreen identities and prepares genuinely new/changed, dynamically admitted art. Its existence is justified by *possible later spawns and changed presentations*, **not** because startup only warms a tiny viewport. Whether actual runs create meaningful new textures must be measured before any removal.
- **Resident memory:** 1-GiB procedural image budget is a hard protection limit, **not** measured GPU VRAM or an invitation to fill 1 GiB. Report (40) shows **zero procedural cache evictions, zero decoded sprite evictions and zero material evictions**. A discard/rebuild/evict loop is therefore **unsupported** in this report; do not remove eviction protections.

## 5. Owner-approved scope / behavior of the new targeted draft

Maintain separate work from [PR #873](https://github.com/joedoragon-glitch/azeroth-chronicles-prototype/pull/873); no merge, Pages/PWA release, or GTA Cuba deployment without explicit approval.

1. Preserve complete current-region terrain and admitted-content loading, Pixi/Canvas fallback, GPU safety, sprite IDs, four classes and v4 saves.
2. Prevent optional **predictive** work from starting during an existing combat encounter and stop its further optional baking at the **next cooperative yield** if a fight begins mid-task; do not introduce per-frame watchers or cancel required visible assets/arrival preparation. Existing synchronous JS operations cannot be preempted mid-instruction; a GPU submission already started may not be safely canceled.
3. Use **tiny aggregated existing-status counters** to distinguish completed predictive scans that found no new art from those that prepared new identities, count total eligible candidates and in-progress combat interruptions. No new user-facing testing menu or per-frame timestamps. This instrumentation can prove an individual scan's value **only on a future build**, not reconstruct unseen past calls in Report (40).
4. Verify with a focused deterministic regression: arrival warms all admitted art; scanning known cached objects causes zero new bakes; newly admitted outdoor objects can still be prepared; a fight starting at a yielded predictive warm stops additional preparation; normal mandatory live actor rendering and full-region loading still work.
5. Keep source-level validation / CI, actual device acceptance and confirmed published-build SHA separate. The next owner test should only be requested when it can distinguish a remaining specific root-cause hypothesis, not simply reproduce the same slow FPS number.

## 6. Next-root-cause plan — order of value

**First:** finish the narrow predictive abort and counters, and validate PR #873 separately; don't publish either automatically. New optional counters are **not a requirement to run another owner playtest immediately**.

**Second:** with the existing Report (40) as baseline, scrutinize `updateQuestGuide()` / `updateNavigationGuide()` / `game.navigationTarget()` / `game.route()` and the precise `otherJsMs` boundaries against the ~100-world-unit incident rhythm. Establish whether the player actually had an active guide in that build before recommending path changes. **Third:** if source-only evaluation cannot distinguish route vs other JS vs runtime GC, add one *bounded opt-in* timing attribution around the two specific guide calls (not a new global profiler). Only then use a short, purposeful matched-device owner reproduction on the **exact installed build SHA**. Compare save timings/predictive counters and the existing work/route diagnostics. Do not ask the owner to run whole-campaign tests just to identify one 200-ms stall.
